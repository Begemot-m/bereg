Сервер:

- `requireUser` берёт сессию и пользователя одним запросом с `include: { user }`

- `getOverrides`/`takenTimes` принимают диапазон дат: month-availability — 60
  дней вперёд, overrides — 30 назад и 90 вперёд, slots — одни сутки.

Проверено отдельно, повторно можно не проверять:

- диапазоны согласованы с `slotsFor`/`monthAvailability` — обе функции считают
  от локальной полуночи, окна на границах суток не теряются;
- индексы под новые `where` уже существуют: `@@unique([userId, startsAt])` у
  `SlotOverride`, `@@index([psychologistId, startsAt])` у `Appointment`;
- `ConsentGate` при `isLoading` отдаёт `children` — барьером перед приложением
  он не является, хотя и висит в `layout.tsx`.

### Что осталось

1. **Baseline (пункт 1) так и не снят** — нужен авторизованный доступ к
   продакшену. Все правки выше сделаны по коду, без измерений «до/после».
2. Карточка клиента `/clients/[id]` всё ещё поднимает 6 запросов сразу:
   `client`, `appointments`, `homework`, `moods`, `client-therapy` + список
   `clients` при инвалидации. Первый кандидат на bootstrap endpoint (пункт 3).
3. `requireUser` по-прежнему вызывается в каждом endpoint — 6–7 раз на экран.
   Bootstrap-эндпоинты решают это заодно.
4. Telegram SDK грузится там, где не нужен, — не трогали.
5. Ветка не смержена в `master`, деплой не делался.

## Деплой: что работает и что блокирует автоматизацию

GitHub Actions workflow `.github/workflows/app-deploy.yml`:

1. `check` — работает;
2. `build` — работает и публикует `sha-<commit>` и `latest` в GHCR;
3. `deploy` — пока падает, потому что постоянные SSH-секреты не настроены.

Последний проверенный run:

- `https://github.com/Begemot-m/bereg/actions/runs/30548896502`;
- check и build успешны;
- deploy ожидаемо завершился ошибкой из-за отсутствующих SSH-секретов.

Дополнительный блокер: пользователь пропустил S3 и полагается на бэкапы
управляемой БД Beget. `deploy/deploy.sh` всегда запускает `backup.sh`, а тот
требует S3. Поэтому до изменения стратегии бэкапов автоматический deploy
останавливается до миграций.

Не ослаблять это молча. Допустимые варианты нужно согласовать:

1. подключить S3 и оставить строгий `deploy.sh`;
2. добавить явно выбранный режим managed backup с документированной
   ответственностью и отдельной проверкой восстановления;
3. временно делать шифрованный `pg_dump` вне контейнера, но не считать локальный
   файл полноценным внешним бэкапом.

Для следующего доступа на VPS лучше создать отдельного пользователя `deploy`
и постоянный ограниченный ключ, а не возвращать временный root-ключ.

## Подтверждённые причины в коде

### Страница «Сессии»

`frontend/src/app/sessions/page.tsx` сразу запускает:

- `appointments`;
- `month-avail`;
- `work-hours`;
- `overrides`;
- `clients`;
- `subscription`.

`ConsentGate` параллельно загружает `consents`. Итого не менее семи API-запросов
при первом открытии.

`QuickAddBooking` смонтирован даже когда закрыт и безусловно запрашивает клиентов
и подписку. Эти запросы нужны только после открытия быстрой записи.

`ScheduleSetup` содержит `WorkHoursEditor` внутри скрытого `Disclosure`.
Скрытый интерфейс остаётся смонтированным. Часть запросов дедуплицируется React
Query, но код, вычисления и подписки всё равно активны.

`month-availability` после `requireUser` отдельно читает:

- рабочие часы;
- все overrides пользователя;
- все незакрытые appointments пользователя.

### Авторизация

Каждый защищённый endpoint вызывает `requireUser`, который обычно выполняет:

1. запрос живой `Session`;
2. запрос `User`;
3. затем основной запрос endpoint.

Несколько параллельных endpoint превращают открытие одной страницы в десятки
коротких SQL-запросов.

### Неограниченные выборки

- `getOverrides(userId)` читает все overrides пользователя за всё время;
- `takenTimes(userId)` читает все незакрытые appointments за всё время;
- ряд страниц запрашивает данные скрытых модалок заранее.

На пустой базе это почти незаметно, но деградирует по мере накопления данных.

## План аудита

Не ограничиваться «Сессиями».

### 1. Baseline

Для ролей guest/client/psychologist пройти:

- `/`;
- `/clients`;
- `/clients/[id]`;
- `/sessions`;
- `/therapy`;
- `/catalog`;
- `/tools`;
- `/cabinet`;
- `/admin`, если доступен тестовый администратор.

Для каждой страницы записать:

- cold/warm navigation;
- количество API-запросов;
- объём JS/CSS;
- повторные и ненужные запросы;
- самые медленные API;
- количество/форму SQL-запросов;
- ошибки и повторные попытки React Query.

### 2. Быстрые исправления без изменения API

- использовать `enabled` для запросов закрытых модалок и редакторов;
- не монтировать тяжёлые скрытые блоки до открытия;
- добавить `dynamic()` для тяжёлых редакторов/графиков;
- исключить повторные загрузки одинаковых данных;
- настроить осмысленные `staleTime`, `retry`, prefetch;
- не загружать Telegram SDK там, где он не нужен.

### 3. Сокращение API

Для сложных экранов рассмотреть агрегирующие bootstrap endpoints:

- sessions bootstrap;
- therapy/client detail bootstrap;
- cabinet bootstrap.

Один endpoint должен один раз аутентифицировать пользователя и параллельно
получить только необходимые экрану данные. Не создавать универсальный огромный
endpoint для всего приложения.

### 4. PostgreSQL

- ограничить appointments/overrides диапазоном дат;
- проверить индексы фактических `where` + `orderBy`;
- не читать длинные Text/JSON-поля для списков;
- проверить Prisma pool и количество конкурентных запросов;
- для тяжёлых запросов снять `EXPLAIN (ANALYZE, BUFFERS)` на тестовых данных,
  не на персональных данных пользователей.

### 5. Проверки

- существующий `cd frontend && bun run check`;
- тесты новых агрегирующих функций/API;
- статический demo export не должен сломаться;
- production build;
- повторные измерения тех же маршрутов;
- после деплоя `https://metodica-psy.ru/api/health`.

## Рекомендуемый порядок реализации

1. Снять baseline и сохранить таблицу результатов в репозитории.
2. Исправить безусловные запросы скрытых компонентов.
3. Ограничить выборки датами.
4. Повторно измерить.
5. Только если запросов всё ещё много — добавить точечные bootstrap endpoints.
6. Оптимизировать общую авторизацию, не ослабляя немедленную блокировку и отзыв
   сессий.
7. Добавить производительные регрессионные проверки.
8. Выкатить образ с уникальным `sha-*`, применить только `migrate deploy`,
   проверить health и ключевые страницы.

## Что не делать

- не использовать `prisma migrate reset` или `prisma db push` в production;
- не класть `.env`, `DATA_KEY`, токены или пароли в git/GitHub Issues;
- не удалять проверку живой сессии ради скорости без замены, сохраняющей отзыв;
- не объединять все данные приложения в один глобальный endpoint;
- не считать animation duration единственной причиной без сетевых измерений;
- не выкатывать через текущий `deploy.sh`, пока не решён обязательный бэкап;
- не менять вид и сценарии продукта под видом оптимизации.
