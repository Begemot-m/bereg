# Хроника — контекст проекта для AI-агентов

Прочитай это перед работой. Проект ведётся несколькими AI-инструментами по очереди через git.
Рабочее название приложения — **«Хроника»** (бренд в `frontend/src/lib/brand.ts`). `bereg` — историческое имя репозитория, а ключи `bereg_*` в localStorage остались от прошлых названий: их не переименовываем, это сломает деплой и данные пользователей. Домен прода — `chronika.space`, и он единственный: других адресов у приложения нет, в ссылках и конфигах их быть не должно.

## Старт в новом чате

Владелец работает с нескольких компьютеров, в Claude Code и в Codex. Единственный источник
правды — git, не память инструмента. Порядок:

1. `git pull --ff-only` — **до** любых правок;
2. `git status` — посмотреть, не осталось ли незакоммиченного от прошлого инструмента;
3. прочитать этот файл целиком (он короткий) — раздел «ТЕКУЩАЯ ЗАДАЧА» ниже говорит, чем заняты сейчас;
4. **дальше читать только тот файл, который нужен под конкретную задачу**, а не все подряд:

   | Файл | Когда открывать |
   |---|---|
   | `CLAUDE.md` | только Claude Code — его локальные правила работы |
   | `PERFORMANCE-HANDOFF.md` | задача про скорость/аудит производительности |
   | `HANDOFF.md` | нужно понять, что уже сделано и что дальше по фичам |
   | `FEATURE-FLOW.md` | добавляем фичу с данными (демо-мок + боевой роут) |
   | `DESIGN-RULES.md` | правила стилей от владельца — первоисточник, короткий |
   | `DESIGN.md` | трогаем UI |
   | `RELEASE.md` / `UPDATES.md` | деплой, миграции, выкатка |
   | `BACKEND.md` | Prisma, API-роуты, база |

   Открыть все семь «на всякий случай» — это ~90 КБ в контексте до первой строчки кода. Не надо.

5. закончил правки — **одна команда, без вопросов и обсуждений**:

   ```bash
   cd frontend && bun run ship "что сделали"
   ```

   Она сама прогоняет `check`, коммитит, пушит, запускает сборку демо и падает,
   если что-то не сошлось. Спрашивать «коммитить ли?» не нужно: это часть
   задачи, а не отдельное решение. Незапушенная работа = следующий инструмент
   начнёт с устаревшей базы, а демо останется на старом коммите.
   Проверить, что доехало: `bun run deploy:status`.

   У Claude Code на это стоит страж: хук `Stop` (`.claude/hooks/unshipped.mjs`)
   не даёт закончить сессию, пока в `master` есть незакоммиченное или
   незапушенное.

### Сделано 19 августа — правила приёма и ручные правки графика

Три пункта владельца.

- **правила приёма слетали при каждом сохранении графика.** `WorkHoursEditor`
  снимал черновик с сервера один раз (это правильно — иначе стираются

  только сам график: `hours`, `sessionMinutes`, `dayFrom`, `dayTo`;
- **запрет на запись стал проверяться на сервере по-настоящему.** Новый
  `checkSlotOpen` (`lib/server/schedule.ts`) отвечает, открыто ли окно:
  снятая дата, занятое время, правило предварительной записи. Через него
  пошли `POST /api/my/appointments` (раньше сверялся только лид и точное
  совпадение занятого времени — записаться можно было в любую минуту, в том
  числе в день, который психолог закрыл руками) и `PATCH
  /api/my/appointments/[id]` (перенос вообще не смотрел на расписание: запрет
  обходился в два касания). Формат записи теперь берётся из самого окна, а не
  из тела запроса. То же самое в демо-моке — `slotOpen` в `lib/demo.ts`;
- **топ-3 запроса в миниатюре карточки.** Отмеченные звёздочкой запросы
  показываются чипами со звёздочкой в карточке каталога (`PsyCard`) и в
  предпросмотре анкеты (`CatalogThumb`). Не отмечено ничего — как раньше,
  строка «Помогаю с…». Общий отбор — `topTopicsOf` в `lib/profile.ts`;
  данные лежат в JSON анкеты, ничего досыпать существующим анкетам не надо;
- **смена шаблона недели не трогает даты, которые правили руками.** Новый
  модуль `lib/schedule-pin.ts`: перед записью нового шаблона даты, на которых
  уже есть правки, «прибиваются» — их окна становятся разовыми (`added`), а
  всё, что принёс бы новый шаблон сверх них, помечается снятым. Дальше график
  ложится только на нетронутые дни. Логика общая для сервера
  (`saveWorkHours`) и демо (`PATCH /work-hours`), миграция не нужна — хватило
  таблицы `SlotOverride`. Тесты — `lib/schedule-pin.test.ts`. Побочный
  эффект, о котором стоит помнить: тронутый день остаётся ручным навсегда,
  вернуть его на шаблон кнопкой пока нельзя.

### Сделано 18 августа — приветствие после верификации, колесо, десктоп

Три пункта владельца плюс выкатка на прод (прод стоял на сборке 15 августа,
поэтому «мобильная колонка» и весь пакет 17–18 августа до него не доезжали).

- **бот пишет о подтверждении анкеты.** До этого одобрение оставляло только
  запись в `Notification` — её видит лишь тот, кто сам зайдёт в кабинет, а
  человек в этот момент как раз ждёт ответа. Теперь в `nudges.ts` появилась
  событийная очередь: `EVENT_NUDGES` (текст, кнопка, путь), `queueNudge` и
  `loadPendingNudges`. Роут `PATCH /api/admin/verification/[id]` при `approve`
  ставит `verified`, воркер `scripts/bot.ts` (`sendEventNudges`) отправляет его
  тем же 30-секундным тиком, что и события расписания. Повтор невозможен:
  `periodKey: "once"` и уникальный ключ «получатель + вид + период», так что
  второе одобрение той же анкеты приветствие не продублирует. Схему не трогали
  — таблица `Nudge` уже была, миграции не нужны;
- **колесо баланса считало проценты по незаполненным сферам.** `initAnswers()`
  ставит все ответы на 5 (середина шкалы), а шапка показывала
  `wheelPercent` по всем восьми сферам — то есть около 50 % ещё до первого
  ответа, и от ползунков число почти не двигалось. У `wheelPercent` появился
  необязательный `keys`; пока колесо собирают, `balance-flow.tsx` считает по
  пройденным сферам и той, что заполняют прямо сейчас. На экране результата
  считается по всем, как и раньше, — полосу `wheelBand` тоже кормим полным
  значением;
- **Telegram на компьютере: колонка включалась не всегда.** Две причины.
  `WIDE_FROM` в `phone-shell.tsx` был 520 px, а контейнерные запросы в
  `app-shell` переключаются на десктопную раскладку с сайдбаром уже с 448 px
  (`@md`): окно шириной 448–519 открывалось широким видом без колонки. Порог
  опущен до 448. Вторая — ожидание `telegram-web-app.js`: он подключается
  стратегией `afterInteractive`, а опрос жил 24 попытки по 40 мс, меньше
  секунды. Не успел скрипт — колонки нет до конца сессии. Теперь ждём до 15 с
  шагом 120 мс и меряем на каждом шаге;
- **знакомство больше не проходится заново на втором устройстве.** Отметка
  `bereg_onboarded` лежит только в localStorage, поэтому Telegram на
  компьютере вёл давно работающего человека через знакомство и выбор роли
  снова — это и была «другая версия по содержанию». Согласие на обработку
  данных живёт в базе и даётся на последнем шаге знакомства, то есть само по
  себе доказывает, что оно пройдено: `ConsentGate` при `pd` + `health` текущей
  редакции зовёт новый `markOnboardedFromServer()`. Роль и анкета
  синхронизировались с сервером и до этого (`applyServerRole`,
  `applyServerProfile`);
- **что между устройствами всё ещё расходится** (сознательно не трогали): флаги
  «уже видел» вида `bereg_guide_done`, `bereg_home_hidden`,
  `bereg_clients_help_seen`, `bereg_modules_teaser_hidden`. На новом устройстве
  подсказки и гид показываются заново. Серверного хранилища под них нет, а
  завести его — это миграция; в пакет с выкаткой на прод не брали.

### Сделано 17 августа — аудит онбординга по приглашению (пункт 4)

Разобран весь путь «клиент пришёл по ссылке»: `inviteCode` → бот
(`psy_` / `inv_`) → `startParam` → `InviteWelcome` → `/api/invite/accept` или
`/api/clients/join`. Подбор кода закрыт с самого начала (подпись HMAC, 60 бит),
а вот три дыры были реальными.

- **пересланная именная ссылка занимала карточку навсегда.** Код `inv_<id>-<подпись>`
  подписан только номером и не истекал: любой, кому переслали переписку, мог
  подключиться к карточке с историей встреч, заданиями и заметками, а настоящий
  клиент после этого получал 409 — и снять чужой аккаунт можно было только
  удалив карточку вместе с историей. Теперь: `inviteFresh` в
  `lib/server/invite-code.ts` (`INVITE_TTL_DAYS = 30`, отсчёт от `invitedAt`,
  для старых карточек — от `createdAt`), `/clients/join` отвечает 410 `expired`,
  а «Отправить» в карточке всегда обновляет `invitedAt` — просроченную ссылку
  специалист высылает заново, и она снова работает. Правило под тестами
  (`invite-code.test.ts`);
- **отвязка аккаунта** — `PATCH /clients/:id { detach: true }`: `userId`,
  `joinedName` и `invitedAt` сбрасываются, `link` → `none`, `TherapistLink`
  помечается `detached`. Записи, задания и заметки остаются. В карточке под
  блоком «Профиль клиента подключён» появилась строка «Подключился не тот

### Сделано 17 августа — бесплатное размещение в каталоге (сервер)

Решение владельца: место в каталоге больше не продаётся. Деньги переезжают на
подтверждение записи и на клиентов сверх трёх. Порядок в выдаче не покупается —
выше стоит тот, кто чаще заходит.

**Новая миграция `20260817180000_free_catalog`** — `User.catalogTrialAt`
(разовый пробный месяц), `Client.pending` (карточка из неподтверждённой
заявки), индекс `Visit(userId, createdAt)` под расчёт активности. Аддитивная,
откат образа базу не ломает.

Правила целиком живут в `lib/server/access.ts`:

- **каталог бесплатный.** `catalogPlacement` теперь смотрит только на
  `status === "approved"`: подписка не добавляет ни места, ни строчки выше.
  Причина — специалист, которого не видно, не получит клиента и никогда не
  узнает, работает ли канал, то есть платить ему не за что;
- **порядок в каталоге — `activityRank`**: заходы за 30 дней, при равенстве
  свежесть последнего, дальше прежняя сортировка по цене. Подписка на порядок
  не влияет вообще;
- **пробные 14 дней переехали с первой сессии на верификацию** (`TRIAL_DAYS`,
  отсчёт от `PsyProfile.reviewedAt`). Их получает **каждый** верифицированный,
  это единственный пробный период на платформе. Тем, кто верифицирован раньше,
  счётчик не начинается заново — он идёт с их собственной даты одобрения, и у
  прошедших верификацию больше двух недель назад пробный период уже истёк;
- **гейт `confirmGate`**: PRO → свободное место из трёх → `NEEDS_PRO` (402).
  Единственная точка, где платформа берёт деньги за приведённого человека;
- **самозапись больше не отбивается** (`POST /api/my/appointments`): записаться
  можно к любому одобренному. Новая карточка помечается `pending` и места в
  лимите не занимает, пока встречу не подтвердили. Приглашение специалистом,
  ручное добавление и прикрепление через «Терапию» лимит трёх мест соблюдают
  как раньше;
- в демо (`lib/demo.ts`) то же самое: самозапись проходит всегда, подтверждение
  без свободных мест — 402.

## Что это
«Хроника» — платформа для психологов (Telegram Mini App + веб). Три роли: **гость / клиент / психолог**. Психолог ведёт клиентов, записи, задаёт рабочие часы; клиент записывается в свободные окна. Центр-создатель — «Амур и Психея» (упомянут в кабинете). Живой прототип: https://begemot-m.github.io/bereg/

## Стек
- **Next.js 15 (App Router) + TypeScript**, фронт и бэк в одном проекте (`frontend/`).
- **Tailwind v4**, **motion** (framer-motion) для анимаций, **@phosphor-icons/react** для иконок.
- **Prisma + PostgreSQL** и API-роуты (`src/app/api`) — для боевого режима. НЕ используются в демо.
- **Демо-режим** (`NEXT_PUBLIC_DEMO=1`): всё работает в браузере на моках в `localStorage`, без бэкенда. Именно он задеплоен.

## Как запускать (папка frontend/)
```bash
bun install
bun run demo        # демо на моках → http://localhost:3000  (для разработки/просмотра)
bun run build       # прод-сборка
bunx tsc --noEmit   # проверка типов
```

## Деплой (важно)
Пуш в ветку `master` на GitHub (`Begemot-m/bereg`) → GitHub Actions собирает **статический экспорт** демо и публикует на GitHub Pages. Настроено в `.github/workflows/deploy.yml`.
- Статическая сборка: `STATIC_EXPORT=1 NEXT_PUBLIC_DEMO=1 PAGES_BASE_PATH=bereg`, CI удаляет `src/app/api` (в статике не нужен).
- `next.config.mjs` включает `output: "export"` и `basePath` только когда `STATIC_EXPORT=1`.
- Значит: **любая правка → git push → через ~2 мин на сайте**. Ломать статический экспорт нельзя (нет серверных `redirect()` в страницах, динамические роуты требуют `generateStaticParams`).
- **Пуш не считается выкаткой.** Бывало, что пуш не рождал сборку вовсе (зависшая очередь Pages), и демо неделю жило на старом коммите при зелёном локальном чеке. Поэтому вместо голого `git push`:
  ```bash
  cd frontend && bun run ship "что сделали"   # check + commit + push + сборка демо
  ```
  Внутри — `deploy:demo`: он пушит, явно запускает workflow (push-триггер в этом репозитории молчит) и двигает тег `demo-live` на выкаченный коммит. Молча «выкачено» больше не бывает.
- Проверить руками, что сейчас в демо: `curl -s https://begemot-m.github.io/bereg/version.json` — там `build` и `sha` выложенной сборки.
- Если сборка не появляется или висит в очереди — первым делом смотри https://www.githubstatus.com: при авариях Actions/Pages пуши перестают создавать сборки вообще. Скрипт такую аварию распознаёт и говорит прямо.

## Массовые рассылки из бота
Разовый анонс всем пользователям (`sendPhoto`/`sendMessage` по списку из базы) —
операция необратимая: отправленное не отзывается, а повторный запуск дублирует
сообщение живым людям. Поэтому скрипт рассылки обязан:

- **вести журнал отправок** — дописывать `chat_id` в файл сразу после успеха, с
  `buffering=1`. На старте читать журнал и выкидывать из очереди тех, кто в нём
  уже есть. Без этого обрыв сети посреди прогона оставляет серую зону: кому
  дошло, а кому нет, узнать нельзя — Telegram истории отправок не отдаёт;
- **переживать сетевые сбои** — 3–4 попытки с нарастающей паузой на таймауты и
  разрывы TLS, а не падать с трейсбеком (18 августа рассылка так оборвалась на
  49-м из 113 адресатов);
- **кэшировать `file_id` картинки** — первому получателю фото уходит файлом, из
  ответа берётся `file_id`, дальше в запросе идёт он. Иначе каждый адресат
  заново тянет мегабайты;
- **держать темп** ~20 сообщений в секунду (лимит Telegram около 30) и молча
  проглатывать `403` (заблокировал бота) и `chat not found` (никогда не писал
  боту) — на сотне адресатов это норма, а не ошибка;
- **начинать с одного получателя** — своего chat_id, чтобы увидеть вёрстку
  поста до того, как он уйдёт всем.

Роль психолога в базе называется `psychologist` (не `psy` — так зовётся только
префикс кодов приглашений). Получателей брать через
`roles: { has: "psychologist" }`.
