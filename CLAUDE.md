# Claude — правила для проекта «Методика»

Перед работой прочитай **[AGENTS.md](AGENTS.md)** (общий контекст), **[HANDOFF.md](HANDOFF.md)** (как запустить, что сделано, что дальше) и **[DESIGN.md](DESIGN.md)** (дизайн-система: тон раздела, шесть правил, готовые классы). UI собирай из классов DESIGN.md, а не инлайном.

## Язык
Всегда отвечай на русском.

## Стек
- Frontend/Backend в одном Next.js 15 (App Router), TypeScript
- Демо-режим (`NEXT_PUBLIC_DEMO=1`) — моки в localStorage, именно он задеплоен на Pages
- Tailwind v4, motion (framer-motion), @phosphor-icons/react
- Пакетный менеджер — **bun** (не npm/yarn)

## Стиль кода
- TypeScript предпочтительнее JavaScript
- Python (если появится): type hints обязательны, Pydantic для схем
- Не добавляй комментарии к очевидному коду
- Не добавляй docstrings, если не прошу явно
- Не создавай README и документацию без явной просьбы
- Иконки только из Phosphor

## Поведение
- Читай только нужные файлы, не сканируй весь проект без причины
- Не рефактори код за пределами запрошенного изменения
- Не добавляй обработку ошибок для невозможных сценариев
- Не добавляй логирование, если не прошу
- Перед крупными изменениями (>3 файлов) — спроси подтверждение
- **Перед началом работы — `git pull`; после — `git commit` + `git push`** (проект ведётся несколькими инструментами по очереди, иначе рассинхрон)
- git commit/push делай, когда правки готовы и проверены — это ожидаемая часть флоу деплоя (пуш в master → GitHub Pages)

## Стиль письма
- Применяй humanizer ко всем текстовым ответам на русском: живой голос, без канцелярита и шаблонов
- Никаких «таким образом», «следует отметить», «в заключение», «немаловажно»
- Пиши как думающий человек, а не как корпоративный отчёт

## Экономия токенов (рабочий режим по умолчанию)
Самое дорогое — длина сессии и картинки. Держи дисциплину:
- **Не делай скриншоты для проверки.** Полагайся на `bunx tsc --noEmit` и точечное чтение кода. Скриншоты/визуальную проверку — только если пользователь прямо просит.
- **Читай файлы срезами** (`offset`/`limit`), а не целиком. Сначала `grep`/`Grep` до нужных строк, потом читай только их. Файлы тут большие (`catalog/page.tsx`, `sessions/page.tsx`, `client-detail.tsx` — сотни строк).
- **Не перечитывай файл, который только что отредактировал** — состояние отслеживается.
- **Широкая разведка по коду — субагентом** (Explore/Task): он читает и возвращает выжимку, большие файлы не оседают в основном контексте.
- **Не повторяй код, который уже есть в контексте.** Показывай только изменённые части.
- **Массовые правки — только через Edit, не через скрипты в PowerShell.** Скрипт, переписывающий файл целиком, заставляет харнесс заново влить весь файл в контекст как «файл изменился» — на больших файлах это десятки тысяч токенов за одну правку. Скриптом можно только то, что Edit не умеет: одинаковая замена по всему проекту (регулярка по десяткам файлов).
- **Дроби работу на сессии.** Закончили логический блок → лучше начать новую сессию («прочитай HANDOFF.md и делаем X»), чем тянуть один разросшийся диалог: контекст уже в HANDOFF/AGENTS/DESIGN.
- `git pull` в начале — чтобы не переделывать правки на устаревшей базе.

## Обновления после релиза
Правила выкатки — в **[UPDATES.md](UPDATES.md)**. Коротко и обязательно:
- в проде только `prisma migrate deploy`, никогда `db push`;
- удаление и переименование колонок — в два релиза, иначе откат кода ломает базу;
- новый расчёт, от которого зависят деньги или данные, пишется сразу с тестом;
- перед пушем `cd frontend && bun run check` (типы + тесты + страж миграций).

## Проверка перед пушем
```bash
cd frontend
bunx tsc --noEmit 2>&1 | grep -v "\.next/types"   # должно быть пусто
```
Демо не должно требовать сервера: новые данные — через `lib/demo.ts` (мок), не через реальные `/api` в демо-режиме. Не ломай статический экспорт (нет серверных `redirect()` в страницах; динамические роуты требуют `generateStaticParams`).
