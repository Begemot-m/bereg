# Как добавить фичу: демо ↔ база

В проекте **два бэкенда за одним клиентом**, и это главный источник трения при доработках. Держи в голове схему — тогда фича не «работает в демо, но не на проде» и наоборот.

## Развязка (факт из кода)

`apiFetch(path, init)` в [`lib/api.ts`](frontend/src/lib/api.ts):

- **демо** (`NEXT_PUBLIC_DEMO=1`, `bun run demo`) → `mockFetch(path)` из [`lib/demo.ts`](frontend/src/lib/demo.ts): всё в `localStorage`, сети нет. Это то, что задеплоено на Pages и показывается людям как витрина.
- **боевой** → реальный `fetch("/api" + path)` с Bearer-токеном и refresh при 401 → роут в `app/api/**` → Prisma → PostgreSQL.

Одна и та же UI-функция дергает `apiFetch("/что-то")`. Значит `/что-то` должно существовать **в обоих** местах.

## Что трогает фича с данными (по порядку)

1. **Клиент** — функция в `lib/<домен>.ts`, зовёт `apiFetch("/route", { method, body })`. Одна на оба режима.
2. **Мок** — ветка в `mockFetch` (`lib/demo.ts`): `if (clean === "/route" && method === "POST") { …работа с db в localStorage… }`. Без неё демо молча отдаст 404.
3. **Схема** — модель/поле в `frontend/prisma/schema.prisma` (если появляются новые данные).
4. **Миграция** — `bun run db:migrate --name коротко_что_добавил`. **Только инкрементально** после первого прода (см. ниже).
5. **Боевой роут** — `app/api/route/route.ts`: `runtime = "nodejs"`, `requireUser(req)` для приватного, **Zod** на теле мутации, фильтрация по `userId` из токена (никогда из тела), `prisma.*`.
6. **UI** — экран/компонент из классов [`DESIGN.md`](DESIGN.md).
7. **Гейт** — `bun run check` (типы + тесты + страж миграций) зелёный → пуш.

## Быстрый путь (UI/текст/стиль)

Не трогает данные → шаги 1–5 не нужны. `bun run demo` → правишь → `bun run check` → пуш. Низкий риск, часто так и будет.

## Read-only vs мутация

- **Чтение** (`GET`): мок отдаёт из `db`, боевой — `prisma.findMany` с `where: { userId }`. Zod не обязателен.
- **Мутация** (`POST/PATCH/DELETE`): Zod на теле **обязателен** (иначе не пройдёт ревью/паттерн), `requireUser`, владение проверяется по токену. В моке — та же логика над `localStorage`.

## Миграции — единственное опасное место

- После первого прода: **только `db:migrate --name …`**, никогда не пересобирать `init` и не `db:push` на боевой — снесёт данные.
- Разрушающее (переименовать/удалить колонку) — **в два релиза**: сначала добавить новое и писать в оба, следующим релизом убрать старое. Между ними и старый, и новый код живы → откат безопасен.
- Страж в `bun run check` роняет CI на `DROP COLUMN` без пометки `allow-destructive`. Правила — в [UPDATES.md](UPDATES.md).

## Где тестить

| Что | Где |
|---|---|
| UI, тексты, стиль | `bun run demo` локально |
| Логика клиента, моки | `bun run demo` + `bun run check` |
| Реальные роуты, схема, миграции | **staging** (`test.murpsy.ru`) на копии базы |
| Деньги (ЮKassa), почта, бот | **staging** с тестовыми ключами |

Правило: **данные и деньги — всегда через staging**, UI — можно сразу.

## Частая ловушка

«Работает в демо, но не на проде» = забыл боевой роут или схему. «Работает на проде, но демо сломано» = забыл ветку в `mockFetch`. Всегда закрывай обе стороны в одном коммите.
