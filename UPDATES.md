# Как выкатывать обновления и ничего не сломать

Короткий рабочий цикл после релиза. Полный план запуска — в
[RELEASE.md](RELEASE.md), архитектура — в [BACKEND.md](BACKEND.md).

---

## 1. Обычный день

```bash
git pull                     # всегда: репозиторий ведут несколько инструментов
# …правки…
cd frontend && bun run check  # типы + тесты + страж миграций
git commit -m "…" && git push
```

Пуш в ветку → выкатка на **staging** (`test.murpsy.ru`).
Слияние в `master` → **production** (`murpsy.ru`).

Если `bun run check` красный — пуш можно и сделать, но CI всё равно
остановит выкатку. Проверяйте локально: там ошибка находится за секунды,
а не за пять минут в логах Actions.

---

## 2. Три вещи, которые ломают прод чаще всего

### Разрушающая миграция

Откат кода **не откатывает базу**. Удалили колонку, что-то пошло не так,
вернули предыдущий образ — а колонки уже нет, и старый код падает на каждом
запросе.

Правило: **удаление и переименование делаются в два релиза.**

| Хочу | Релиз 1 | Релиз 2 |
|---|---|---|
| Переименовать колонку | добавить новую, писать в обе, читать новую | удалить старую |
| Удалить колонку | перестать читать и писать | удалить |
| Сделать поле обязательным | добавить с `@default`, заполнить | поставить NOT NULL |

Страж миграций (`scripts/check-migrations.mjs`) не даст протащить такое
случайно: CI покраснеет. Если изменение осознанное — в файле миграции пишем
причину:

```sql
-- allow-destructive: колонка не использовалась с релиза от 3 августа
```

### Миграция вместо схемы

В проде выполняется **только** `prisma migrate deploy` — он применяет
готовые файлы. Команда `prisma db push` приводит базу к схеме и может молча
снести колонку с данными; в проде её не запускаем никогда.

Новая правка схемы — всегда:

```bash
cd frontend
bun run db:migrate --name add_client_tags   # создаст файл миграции
```

Файл попадает в git и проходит ревью как код.

### Забытая переменная окружения

Приложение падает при старте, если нет `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`
или `JWT_SECRET` — это сделано намеренно: лучше не подняться, чем работать
с пустым секретом. Добавили новую переменную в код — добавьте и в `.env` на
сервере, иначе выкатка встанет на health-чеке и откатится.

---

## 3. Что происходит при выкатке

`deploy.sh` на сервере делает по порядку:

1. Тянет образ.
2. **Бэкап базы прямо сейчас** — не «есть же ночной». Не сделался —
   выкатка останавливается.
3. Применяет миграции отдельным контейнером. Упали — работает старая версия.
4. Поднимает новый образ, запоминая предыдущий.
5. Проверяет `/api/health` — он отвечает только если база доступна.
6. Не ответил за минуту — **сам возвращает предыдущий образ**.

Ручной откат, если понадобится:

```bash
cd /opt/bereg
./deploy.sh ghcr.io/begemot-m/bereg:sha-<предыдущий>
```

Образы хранятся по хэшу коммита, пересборка не нужна — это секунды.

---

## 4. Раз в месяц

- [ ] Восстановить бэкап в staging-базу и открыть приложение. Непроверенный
      бэкап бэкапом не считается.
- [ ] Посмотреть, не растёт ли `SupportRequest` без ответов.
- [ ] Проверить, что метка сборки в кабинете совпадает с последним деплоем.

## 5. Что проверяется автоматически

| Проверка | Где | Что ловит |
|---|---|---|
| Типы | CI, `bun run typecheck` | несовпадение данных между слоями |
| Тесты | CI, `bun test` | шифрование, лимиты частоты, коды входа, прилипание окон, правила отмены |
| Страж миграций | CI | удаление колонок и таблиц без пометки |
| Health-чек | при выкатке | контейнер поднялся, но база недоступна |
| Метка сборки | в приложении | вебвью показывает старую версию из кеша |

Тесты живут рядом с кодом (`*.test.ts`). Новый расчёт, от которого зависят
деньги или данные, — сразу с тестом: он дешевле одного разбора «почему у
клиента слетела подписка».
