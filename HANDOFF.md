## 10 августа 2026 (ночь) — аудит синхронизации: карточка специалиста одна на всё приложение

Владелец заметил: закреплённый в «Терапии» психолог показывался именем без
аватарки. Причина оказалась общей для нескольких разделов.

**Что было сломано:**

- `GET /api/my/therapists` отдавал `{ id, name, active }` — и всё. Страница
  терапии дорисовывала фото, метод, цену и город из статического `PSYS`
  (`lib/catalog.ts`), а в бою `PSYS` пуст: там только демо-анкеты. Отсюда буква
  вместо портрета, пустые чипы, отсутствие галочки и ссылка «в общий каталог»
  вместо анкеты специалиста. Тот же баг — в табах-переключателях терапевтов и в
  блоке ближайшей сессии на главной (`app/page.tsx`, `PsyAvatar`).
- Приняв приглашение (`POST /api/clients/join`), клиент не получал терапевта:
  `TherapistLink` не создавался, а список склеивался только по записям. Человек
  открывал «Терапию» с предложением найти специалиста — того самого, который
  его позвал.
- `GET /api/catalog?id=` фильтровал `status: "approved"`, поэтому анкету
  неверифицированного психолога клиент не видел вообще — вопреки правилу
  «до верификации анкету видит клиент, в каталог — только после».

**Что сделано:**

- Новый `lib/server/psy-card.ts` — единственная сборка публичной карточки
  (`buildPsyCards` / `psyCardsByIds`). Каталог и `/my/therapists` зовут её же,
  поля не расходятся по определению. В карточке появился `verified` — статус
  анкеты, а не константа `true` на клиенте.
- `TherapistStore` (`lib/therapists.ts`) хранит `cards: Record<id, Psy>`;
  `therapistCard(name)` — единственная точка получения карточки для всех
  разделов, с откатом на `PSYS` в демо. Закрепление из каталога кладёт карточку
  в кэш сразу, до ответа сервера.
- `/clients/join` заводит `TherapistLink`, а список терапевтов дополнительно
  склеивается по карточкам `Client` — старые связи, заведённые до этой правки,
  тоже подтянутся.
- `?id=` в каталоге отдаёт анкету любого статуса; общая выдача по-прежнему
  требует `approved` + размещение (PRO или 14 дней).

**Остаётся (по тому же аудиту, руки не дошли):**

1. `availability`/`availableTimes` в карточке считаются только по шаблону недели
   (`availabilityFromWorkHours`), без занятых окон, — фильтр «когда удобно»
   может показать специалиста на время, которое уже занято. `nextDays` рядом
   считается правильно.
2. Своя карточка-предпросмотр (`profileToCatalogPsy` → `nextSlotDays`,
   `lib/availability.ts`) считает «ближайшее окно» другим алгоритмом, чем сервер
   для чужих карточек: психолог видит у себя не то число, что клиент.
3. Прикрепить (`PATCH /my/therapists`) и записаться (`POST /my/appointments`) к
   неодобренному психологу нельзя — для приглашённого клиента это стоит
   разрешить, раз анкету он уже видит.
4. `psy.tg`, точный адрес и `links` каталог наружу не отдаёт вовсе — блок
   «Написать в Telegram» в бою работает только на своей карточке.
5. Профиль психолога де-факто ведётся из localStorage (`bereg_psy_profile`),
   сервер — зеркало с дебаунсом 1.5 с. Правки с двух устройств подряд затирают
   друг друга.

**Прод отстаёт от master.** На VPS образ `sha-b4357aa`, применено 12 миграций из
15. Не выкачены: `client_personal_card`, `active_role_therapist_links`,
`reviews` — и код трёх последних коммитов вместе с этим.

## 10 августа 2026 (вечер) — синхронизация: всё в базе, ничего в браузере

Аудит показал, что часть данных жила только в localStorage, а часть боевых
роутов не делала того, что делал демо-мок. Три коммита подряд.

**Ломалось в проде и починено:**

- `GET /api/clients/:id` не существовало вовсе — экраны карточки клиента, его
  домашек и заметок получали 405. Роут добавлен.
- Сервер не считал статистику клиента. `GET /clients` отдавал сырую строку
  Prisma, а тип обещал `sessionsDone/hoursDone/nextAt/lastAt/hwTotal/hwDone`:
  в проде у каждого клиента было «0 сессий», и `derivedStatus` показывал
  «Пауза». Считает `lib/server/clients.ts` группировками.
- `PATCH /clients/:id` выбрасывал `status` и `joinedName`. Колонка `joinedName`
  добавлена, оба поля принимаются.
- `PATCH /my/therapy` у человека без психолога возвращал пустой ответ и терял
  патч: настроение и колесо баланса не сохранялись. Теперь заводится **личная
  карточка** (`Client.psychologistId` стал nullable).
- Приглашение клиента никогда не принималось: метка из `?invite=` ложилась в
  `sessionStorage` и там оставалась. Появился `POST /api/clients/join`, в
  ссылке теперь подписанный токен (`createInviteToken`), а не номер карточки —
  по номеру подключались бы к чужой перебором.

**Синхронизация между устройствами:**

- **Терапия одна на человека.** Со вторым психологом заводится вторая карточка,
  и половина истории оставалась в первой. `therapyOwnerId()` сводит настроение,
  колесо и «что хорошего» к самой ранней карточке аккаунта; подготовки к
  встречам остаются по карточкам (психолог видит только свои).
- **Роль в базе** — `User.activeRole`. Приезжает в `/auth/me`, применяется
  через `applyServerRole`, пишется на сервер из `setRole`. `useMe()` теперь
  вызывается в `app-shell`, а не только в кабинете.
- **Закреплённые терапевты** переехали из `bereg_my_therapists_v1` в модель
  `TherapistLink` (`/api/my/therapists`). localStorage остался кэшем: рисует
  список до ответа сервера и держит демо.
- Каталог прикреплял специалиста **без id** — раздел «Терапия» потом не знал,
  чей график показывать. `AttachTherapistButton` получает `psy.id`.
- **Ближайшее окно в каталоге** считалось по одному шаблону недели. Теперь
  `nextFreeSlotDays()` — шаблон минус снятые даты минус занятые окна, с
  правилом предварительной записи. Есть тест.

**Оценки — новая фича.** Их не существовало: каталог проставлял всем боевым
карточкам `rating: 0, reviews: 0`, сортировка «по рейтингу» сравнивала нули.
Модель `Review` (одна оценка на пару, можно переписать), `GET/POST /api/reviews`,
звёзды в карточке терапевта (`RatingRow` в `app/therapy/page.tsx`). Оценить
можно только после состоявшейся встречи — проверяет сервер. Каталог берёт
среднее и число оценок из базы, `newcomer` теперь значит «нет ни одной оценки».

**Не сделано:** текст отзыва принимается сервером, но в интерфейсе только
звёзды; списка отзывов на странице специалиста нет. Запрет отмены и флаг
онбординга всё ещё дублируются в localStorage (сервер отдаёт `cancelLockDays`
вместе с записью, локальное значение — запасное).

**Три миграции ждут выката:** `20260810180000_client_personal_card`,
`20260810190000_active_role_therapist_links`, `20260810200000_reviews`. На VPS
только `prisma migrate deploy`, перед этим свежий бэкап.

## 9 августа 2026 (ночь) — уведомления в боте: напоминание психологу

Очередь `TelegramDelivery` + worker в `scripts/bot.ts` были и раньше (запись,
перенос, отмена обеим сторонам, напоминания клиенту за 24 и 2 часа). Добавлено:

- **Психолог получает напоминание за 2 часа** до каждой сессии.
  `replaceClientReminders` стала `replaceReminders` (`lib/server/telegram-delivery.ts`):
  один вызов пересобирает напоминания и клиенту, и психологу, гасит старые по
  всей встрече. Обновлены четыре роута записей и `PUT /api/my/reminders`.
  Напоминания психологу ставятся и тогда, когда у клиента нет аккаунта, — раньше
  при переносе такой записи не пересобиралось вообще ничего.

Миграций нет, схема не менялась. Владелец решил: бот пишет **только про записи**
— домашки, отметки о выполнении и итоги сессий в бота не уходят (была попытка,
откачена в том же чате). Не сделано: утренняя сводка психологу на день, панель
доставок в админке.

## 9 августа 2026 (вечер) — «Сессии»: список правок закрыт

Десять пунктов владельца по разделу «Сессии» сделаны все. Из них два потянули
за собой базу и логику:

- **Предварительная запись** — новое правило приёма рядом с запретом отмены.
  `WorkHours.leadDaysOffline` / `leadDaysOnline` (миграция
  `20260809120000_booking_lead_days`, только добавление колонок), настройка в
  хвосте редактора графика, очно и онлайн отдельно: до кабинета нужно доехать,
  к звонку нет. Правило применяется на сервере — `leadBlocked()` в
  `lib/server/schedule.ts`, 422 в `POST /api/my/appointments`; чужое расписание
  (`/slots`, `/month-availability` с `psy=`) ближние окна уже не показывает, а
  своё показывает всегда — психолог записывает клиента сам. Тест —
  `lib/server/lead-days.test.ts`. **В проде нужен `prisma migrate deploy`.**
- **Выбор клиента переехал в модалку** (`ClientModal` в `week-windows.tsx`,
  внутри — общий `ClientPicker`). Инлайновый `ClientChips` с поиском по имени
  удалён: поле ввода жило в каждой раскрытой плитке дня, тянуло клавиатуру и
  перерисовывало всю ленту окон на каждую букву — отсюда и лаги при записи в
  окно. Запрос клиентов теперь уходит только когда модалку открыли.

Остальное по мелочи: свободные окна красятся градиентом по времени суток
(`dayTint()` — от светло-зелёного к лавандовому, 07:00→21:00); «?» в графике
чернильный без обводки; красный ярлычок «не задан» у кнопки «График», пока
рабочие часы пусты; «+ новый клиент» убран из шапки быстрой записи (он остался
внутри списка); «Ближайшие» при выбранном сверху дне становится контурной и по
нажатию возвращает на сегодня; в раскрытой записи «Написать» чёрная с белым
текстом, «Освободить» — отдельной кнопкой по центру с крупным крестиком;
в переключателе формата иконка слева от слова; крестики закрытия в окнах —
зелёные в кружке вместо красных; в легенду календаря добавлен пустой кружок
«свободные дни». Инструкции (`SESSIONS_HELP`, `SCHEDULE_HELP`) переписаны под
нынешний вид, добавлена страница про правила приёма.

**Скринов в инструкции по-прежнему нет** — поле `image` у `HelpPage` пустует,
рисуются мини-макеты кодом. Съёмка Playwright'ом отложена: дорого по контексту,

## Состояние на 8 августа 2026 — где остановились (читать первым)

Всё запушено, дерево чистое: `master` = `origin/master` = `374fc71`. Демо на
Pages собрано с этого же коммита (`version.json` → `sha: 374fc71`), тег
`demo-live` на нём же. `bunx tsc --noEmit` чистый. Ничего доделывать за прошлым
компьютером не нужно — можно сразу клонировать и работать (см. раздел 0).

Последние заходы — UI-полировка мобильного приложения, анимации веб-лендинга и
снятие старой колонки ролей с чтения:

- **`role` больше не используется в коде** (8 августа). Решения о ролях целиком
  на `roles[]`: `rolesOf`/`hasRole` больше не имеют фолбэка на старую строку,
  `grantPsychologist`/`revokePsychologist` в неё не пишут. Переведены `/auth/me`
  (поле `role` из ответа убрано), `/auth/telegram` и `/auth/email/verify`
  (отдают `roles`), `POST /profile/role`, список и PATCH в `/admin/users`
  (в списке `roles: string[]`, в PATCH сравнение через `hasRole`). На фронте:
  `Me.roles`, кабинет (`me.data?.roles?.includes("psychologist")`),
  `UserRow.roles` и админка, демо-моки в `lib/admin.ts` и `lib/demo.ts`.
  Колонка в базе осталась намеренно — её снимает следующий релиз, см. техдолг
  ниже.

- **Лендинг, скролл-анимации** (`components/web-landing.tsx`, `374fc71`).
  Появление блоков через blur + подъём (`Reveal`), карточки возможностей
  собираются в липкий стек (`md:sticky` с нарастающим `top`, каждая уходящая
  карточка притухает вуалью и сжимается до 0.92), «Для кого» держит липкий
  заголовок сбоку, герой при скролле сжимается и растворяется, скриншоты идут
  параллаксом. Стек и параллакс — только с 768px (`matchMedia` в хуке), на
  мобиле остаются простые появления. `useReducedMotion` (`calm`) везде
  оставляет только opacity.
- **Каталог** (`79cebc3`): у специалистов галочка-печать как в верификации,

## 0.1. Ролевая модель и верификация психолога (5 августа 2026) — история решения

Основное сделано, раздел оставлен как объяснение, почему роли и верификация
устроены именно так. Незакрытым остаётся только второй релиз перехода
`role` → `roles[]` (пункт 5 ниже). Актуальное состояние — в первой секции файла.

### Что решили

Один аккаунт, две роли, переключение тумблером в кабинете. Правило одно:
**есть заявка — есть тумблер, есть `approved` — есть клиенты.**

- дефолт роли — `client` (был `psychologist` и в localStorage, и в базе);
- выбрал психолога в онбординге → кабинет открыт сразу и целиком, верификация
  идёт параллельно. Мотивация дозаполнить анкету — видеть, ради чего;
- до `approved` анкета не в каталоге и клиентов принимать нельзя;
- зашёл клиентом → тумблера нет, есть «Запросить доступ». Подал заявку —
  тумблер появился, не дожидаясь модерации;
- отказ = `rejected` + текстовая причина, видна в кабинете, подать заново
  можно сколько угодно. Большинство отказов будут «фото диплома нечитаемое»;
- отзыв верификации у действующего психолога: анкета уходит из каталога, новых
  клиентов нельзя, **текущие сессии дорабатываются**. Обрывать человека посреди
  терапии — навредить клиенту сильнее повода. Исключение — жалоба на вред;
- паспорт не просим: биометрия тянет отдельный режим хранения, для проверки
  диплома пользы нет.

### Что уже сделано (коммит от 5 августа)

- `frontend/src/lib/role.ts` — дефолт `client`;
- `frontend/prisma/schema.prisma` — `User.role @default("client")`,
  `PsyProfile`: статусы `draft | review | approved | rejected`, `rejectReason`,

## 2. Развернуть проект

```bash
git clone https://github.com/Begemot-m/bereg.git
cd bereg/frontend
bun install            # postinstall делает prisma generate — БД не нужна
```

## 3. Рабочий цикл

```bash
git pull                                     # ВСЕГДА перед началом (репо ведут несколько инструментов)
# …правки…
cd frontend && bun run check                 # типы + тесты + страж миграций
git add -A && git commit -m "…" && git push origin master   # пуш в master → авто-деплой
```

Те же проверки стоят воротами в CI: пока они красные, сборка и выкатка
не запускаются. Локально это секунды, в Actions — минуты, поэтому гонять
лучше у себя.

**Два деплоя, не путать:**

1. `deploy.yml` — демо на Pages. Пуш в `master` → статический экспорт
   (`STATIC_EXPORT=1 NEXT_PUBLIC_DEMO=1 PAGES_BASE_PATH=bereg`, CI удаляет
   `src/app/api`) → https://begemot-m.github.io/bereg/ (~2 мин).
2. `app-deploy.yml` — боевое приложение в Docker. Сборка (`build`) чинена и
   **проходит** (имя образа приведено к нижнему регистру `ghcr.io/begemot-m/bereg` —
   Docker-тег обязан быть lowercase). Шаг `deploy` (SSH-выкатка) пока падает:
   нужен сервер и секреты `SSH_HOST` / `SSH_USER` / `SSH_KEY`. Подробности — в
   [BACKEND.md](BACKEND.md).

Проследить за сборкой:

```bash
gh run watch $(gh run list --limit 1 --json databaseId -q '.[0].databaseId') --exit-status
```

**Проверка глазами.** Через MCP Playwright: `bun run demo`, вьюпорт 390×844.
Важно: скроллить нужно элемент `.overflow-y-auto`, а не window — страница
сама не прокручивается.

**Если правки «не применились»** — почти всегда кеш вебвью, а не сборка.
В Кабинете внизу показана дата сборки: старая дата = страница из кеша.
Лечится очисткой кеша Telegram и повторным открытием.

подобном без пометки `allow-destructive`. Локально то же самое —
`cd frontend && bun run check`.

## 6. Что НЕ переносится через git (учти)

- Твой домашний `~/CLAUDE.md` — **заменён** на `CLAUDE.md` в репозитории (эта же папка), Claude Code на ноуте подхватит его сам.
- Память Claude Code (`~/.claude/projects/.../memory/`) — локальная для машины, для работы не нужна.
- Состояние демо в браузере (localStorage): онбординг и черновики — свои на каждом устройстве/браузере. Онбординг просто покажется заново — это нормально.
- **Секреты**: `deploy/.env` на сервере в git не лежит и не должен. Образец —
  `deploy/.env.example`. Локальный `frontend/.env.local` (`DATABASE_URL`,
  `JWT_SECRET`, `TELEGRAM_BOT_TOKEN`) тоже локальный — для демо он не нужен, а
  для боевого режима собирается заново из `frontend/.env.example`.
- **Исходные PNG маскотов, настроений и практик** (`frontend/public/mascots/*.png`,
  `mood/*.png`, `practices/*.png`) — в `.gitignore`: в сборку едут только webp,
  и они в git есть. Приложение на новой машине выглядит нормально; исходники
  понадобятся только если картинки пережимать заново — тогда взять их со старого
  компьютера или сгенерировать снова.
- `.claude/settings.local.json` — локальные разрешения Claude Code, на новой
  машине наберутся сами.
- Первый запуск на ноуте: `gh auth login` (для деплой-логов), логин в Claude
  Code и, если нужна проверка глазами, `/mcp` → включить Playwright.

## 7. Чего делать не надо (проверено на своей шкуре)

- **Не собирать без `STATIC_EXPORT=1` и не думать, что проверил Pages.**
  Это две разные сборки. CI ещё и удаляет `src/app/api` — локально это
  повторяется копированием папки во временное место.
- **Не трогать `prisma db push`** на боевой базе. Только `migrate deploy`.
- **Не сносить блоки, которые «выглядят лишними»**, не сверившись: блок
  подписки в кабинете и плюсик в сессиях так уже удалялись по ошибке.
- **Не считать «не применилось» багом кода** до проверки даты сборки в
  Кабинете — трижды это оказывался кеш вебвью.

## 8. Админка: состояние и что дальше (5 августа 2026)

Вход в админку в **демо** прячется за признаком: открыть прототип с `?admin=1`
(снять — `?admin=0`), флаг живёт в localStorage `bereg_demo_admin`. Раньше в
демо стоял `isAdmin: true` — админку видел любой посетитель прототипа; голый
`false` вместе с этим спрятал её и от владельца. В **проде** доступ прежний:
`isAdmin` в базе + username `mmgorba`, проставляется при каждом входе через
Telegram.

**Сделано в этот заход:** очередь верификации психологов. `GET
/api/admin/verification` (очередь + последние 10 рассмотренных), `PATCH
/api/admin/verification/[id]` с `approve` / `reject` + причина. Решение пишется
в аудит и уходит человеку уведомлением; при одобрении роль дотягивается до
`psychologist`. Клиентские хуки и демо-моки — `frontend/src/lib/admin.ts`
(сводка и список пользователей тоже переведены на хуки, иначе в демо админка
падала на реальных `/api`). До этого анкеты со статусом `review` можно было
одобрить только руками в базе — то есть боевая верификация была замурована.

**Сделано следующим заходом (5 августа, вечер):** поддержка, журнал и роль.

- `GET /api/admin/support` — открытые обращения от самого старого + последние
  10 разобранных; `PATCH /api/admin/support/[id]` с `handle` (можно с `reply`)
  и `reopen`. Ответ уходит уведомлением, если у человека есть аккаунт; гостю
  писать некуда — там только контакт, закрытие просто фиксирует факт. Текст
  обращения не трогаем: это единственное свидетельство.
- `GET /api/admin/audit` — журнал с фильтром по префиксу действия
  (`admin.`, `login`, `consent`) и постраничной выдачей. В UI грузится только
  когда раскрыли `details`: записей там больше, чем всего остального.
- Смена роли — в существующем `PATCH /api/admin/users/[id]`, поле `role`.
  Каталог смотрит на статус анкеты, а не на роль, поэтому перевод в клиенты
  снимает approved-анкету в `draft` (текст остаётся). Человеку уходит
  уведомление, решение — в аудит.
- Демо: обращения в `bereg_demo_support`, роли в `bereg_demo_roles`, журнал —
  статичный сид. Счётчик обращений в сводке теперь считается по тому же моку,
  а не жёстко «2».

**Сделано следом: ряды по дням и история платежей.**

По дороге выяснилось, что ряд оплат строить не из чего: `Subscription` — одна
строка на психолога, и вебхук ЮKassa перезаписывал в ней последний платёж.
Сколько денег пришло за месяц и сколько из этого продления — ответа не было
нигде. Поэтому:

- новая таблица `Payment` (строка на платёж, `yookassaPaymentId` уникален,
  сумма в копейках, `kind` = initial | renewal). Миграция
  `20260805210000_payment_history` — **только добавление**, откат кода базу не
  ломает. **В проде нужен `prisma migrate deploy`, иначе `/api/admin/series`
  упадёт на отсутствующей таблице.**
- пишет `recordPayment` (`lib/server/payments.ts`) из вебхука и из
  автопродления, идемпотентно по id платежа. В вебхуке запись стоит **до**
  выхода по идемпотентности: подписку мог уже продлить `renew.ts`, и деньги
  иначе не попали бы в историю. `getPayment` теперь возвращает сумму.
- задним числом таблица не наполняется: восстановить можно факт последнего
  платежа, но не сумму, а подставить текущую цену — записать в отчёт о деньгах
  выдуманное число. История начинается с выкатки, в UI это подписано
  (`paymentsSince`).
- `GET /api/admin/series?days=30|90` — регистрации (`User.createdAt`), записи
  (`Appointment.createdAt`, без отменённых), оплаты и выручка. Сутки режутся по
  Москве, иначе «сегодня» начинается в три ночи. Расчёт вынесен в
  `lib/server/series.ts` и покрыт тестами (`series.test.ts`): дни без событий
  обязаны остаться в ряду нулями, иначе провал выглядит ровной линией.
- в админке блок «Динамика» с переключателем 30/90 и тремя спарклайнами.
  Демо-ряд считается детерминированно от номера дня.

**Сделано следом: воронки.** `GET /api/admin/funnel` — две цепочки за всё
время, блок «Воронки» в админке под «Динамикой».

- Психолог: регистрация → завели анкету (`PsyProfile` появляется на первом
  сохранении) → подали (`submittedAt`) → одобрены (`status = approved`, это
  же и «в каталоге»: каталог фильтрует ровно по нему) → первая запись.
- Клиент: аккаунт → записались → сессия состоялась (`status = done`) →
  пришли второй раз. **Шагов «зашёл в каталог» и «открыл карточку» нет:
  просмотры страниц нигде не пишутся.** Вывести их из записей значит нарисовать
  100 % конверсию каталога — это будет вранье в отчёте, где как раз и ищут
  дырку. Понадобятся — нужна отдельная таблица событий.
- База обеих воронок — пришедшие сами: пользователи, у кого нет карточки
  клиента с `invitedAt`. Приглашённый психологом клиент платформу не выбирал,
  в знаменателе ему не место — иначе активный психолог с двадцатью клиентами
  «портит» конверсию.
- Проценты считаем и от начала, и от предыдущего шага (`lib/server/funnel.ts`,
  тесты `funnel.test.ts`): только от начала — и провал размазывается по всей
  цепочке, не видно, на каком шаге он случился.

**Что осталось, по приоритету:**

1. Когорты по неделе регистрации: кто вернулся на 2-й и 4-й неделе.
2. Деньги: MRR, конверсия `pending → active`, сколько истекло без продления.
   Теперь считается по `Payment`, а не по последней строке подписки.
3. Каталог: сколько approved реально заполнили рабочие часы и получают записи.
   В воронку шаг про часы не вошёл: записи бывают и без заполненного
   расписания (психолог заводит клиента руками), ступень получилась бы
   немонотонной.
4. Доставка Telegram-уведомлений (`TelegramDelivery`): процент недоставленных —
   ранний признак поломки бота.
5. Второй уровень доступа — модератор (только верификация и поддержка, без
   денег и блокировок). Сейчас админ ровно один и зашит в код строкой; заодно
   стоит привязывать владельца по `telegramId`, а не по нику: ник в Telegram
   меняется, и доступ теряется молча.
